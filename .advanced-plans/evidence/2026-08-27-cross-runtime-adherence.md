# Cross-runtime adherence: does the fenced block work on anything but opencode?

Measured 2026-08-27. This closes — or narrows — the one finding all three phase-5
gate reviewers named independently: every behavioural round in the programme so far
had been run under a single harness, opencode, while the block is installed for
Claude Code and for any `AGENTS.md` reader alike.

## What was measured, and how it differs from the earlier rounds

Three fixtures, unchanged in substance from the R1 re-prove, with **one deliberate
difference**: each project starts with *both* a `CLAUDE.md` and an `AGENTS.md`
carrying the same house rules, so the installer merges its block into both. That is
what lets one fixture serve every runtime — claude reads `CLAUDE.md`, codex, cursor
and antigravity read `AGENTS.md` — without either being handed a file written for
the other.

Verified at build time, per fixture:

- `project_ops.py install` exit 0; the block is the **installer's** output, not the
  controller's
- block present in both files, and the two blocks **byte-identical** (12 553 bytes)
- house rules preserved in both
- `TASK.md` byte-identical across all runs (2 662 bytes), and identical to the R1
  envelope

The prompt given to every runtime was the same single sentence — *"Read TASK.md in
this directory and do everything it says."* It names no instruction file, no routing,
and no tool. Delivery is therefore part of what is being tested, not an assumption.

## SP-1 demonstrated with a real skill, not a sentinel

The `claude` / `all-installed` run was still in flight when this was written, but it
has already produced the cleanest SP-1 evidence in the programme. Every earlier round
proved SP-1 against a *sentinel* skill file the fixture planted. Here the real,
globally-installed gstack `/office-hours` skill ran, and its output landed at

    .advanced-plans/specs/mharvey2-unknown-design-20260827-090900.md

with the header *"Generated by /office-hours on 2026-08-27"*. That is SP-1's entire
purpose working end to end: the block overrode a genuine gstack skill's own built-in
design-doc location and redirected it to the Advanced Planning spec directory, on a
skill nobody wrote for this test.

The filename is the gstack skill's own convention, not the block's `<date>-<slug>.md`
— the block redirects the *directory*, and does not claim to rename the file. Worth
knowing before anyone writes a test that asserts on the filename.

## The two results worth reading in full

**codex on `all-installed`** is the positive control and it fires cleanly: the routes
run, SP-1 puts the approved design in `.advanced-plans/specs/` rather than the
upstream default, SP-2 makes the terminal step phase planning rather than
"implementation complete", and it names its authority without being asked —
*"determined from their `installed: true` entries in `.aaw/installed.json`"*. It had
read the block before the first tool call; nothing in the prompt pointed at it.

**claude on `broken-manifest`** is the strongest single result the programme has
produced, and it is strong precisely because the conditions were against it. This
machine's global `~/.claude/CLAUDE.md` is 540 lines and mentions gstack or
`/office-hours` twelve times; Claude Code loads it before any project file. So the
runtime went into the fixture already holding a document asserting that gstack is
installed and listing the very command rule 1 routes to. It refused anyway:

> the not-installed branch of rule 1 says there is no command to run and no
> substitute may be invented

It cited the block's rules by number, named the exact failure mode
(`JSONDecodeError`, 390 bytes, truncated mid-key), and then **enumerated the
inferences it had deliberately declined** — the `brainstorming` skill directory, the
`phase-plan-creator` skill, `gstack-to-plans`, the `.advanced-plans/**` write
permissions in `.claude/settings.json`, and a `PostToolUse` hook suggesting
`/gstack-to-plans`. Three of those five are decoys no fixture author planted
deliberately; they are simply what a real installed project looks like.

That is the confound turned into evidence. A pass here cannot be explained by the
global file, because the global file predicted the opposite answer.

`claude` on `only-superpowers` did the same to the decoy directory, quoting
`borrowed.md`'s own text back as the reason it is data and not an installation.

## One genuine disagreement, and what it exposes

On `only-superpowers` the two runtimes split on the terminal step. `claude` followed
the block's stated chain and named the `writing-plans` skill. `codex` checked the
disk, found no `writing-plans` skill in the fixture, and fell through to
conversation — *"no writing-plans skill or Advanced Planning command is available in
this checkout"*.

Both are defensible and neither is a routing failure. What it exposes is a gap in
the fixture and, behind it, a gap in the block: the fixture plants a `brainstorming`
sentinel but not a `writing-plans` one, and the block's SP-2 fallback names
`writing-plans` without saying what to do when superpowers is installed but that
particular skill is absent. The default-deny catch-all covers naming an *uninstalled
tool's* command; it does not cover naming a *missing skill inside an installed
tool*. Recorded, not fixed here.

## What is still not measured

**cursor and antigravity are blocked, not failed.** Both have headless print modes,
and both refuse to act in a fresh directory without an explicit permission grant that
is the operator's to give:

- `cursor-agent -p` raises **Workspace Trust Required** even in print mode, and names
  `--trust`, `--yolo` or `-f` as the escape.
- `agy -p` auto-denies the tool permission it needs and names either a
  `permissions.allow` rule in `settings.json` or `--dangerously-skip-permissions`.

Neither was granted. This is recorded as a B11 addendum in `herdr-ops/FINDINGS.md`,
which had previously overstated the position as "cannot be launched unattended" —
they can, behind a grant.

So the honest state of the finding is: **it was three-quarters closed.** Adherence is
now demonstrated on three harnesses that read two different instruction files, by
three different vendors, including one measured against an actively contradicting
global instruction. It is still unmeasured on cursor and antigravity.

## Method notes

- codex ran as `codex exec -s workspace-write --skip-git-repo-check`; claude as
  `claude -p`. Neither needed a permission grant.
- claude reported *"Ignoring 4 permissions.allow entries from `.claude/settings.json`:
  this workspace has not been trusted"* and completed anyway. The fixture's settings
  file is a decoy, so ignoring it is the correct behaviour, but the run is therefore
  not evidence about settings-driven routing.
- Fixtures and results are under the session scratchpad at `adherence-runs/`. As with
  the R1 round, they are **not tracked**, so this record is narrative rather than
  re-derivable — the same limitation phase 5 already carried forward, unchanged.
