# Block adherence

Does a coding agent that reads the AAW routing block actually behave differently
because of it?

Every other suite in `tests/` checks that the block is *installed* correctly —
merged into the right files, idempotently, preserving what the user wrote. None
of them checks that it is *obeyed*. That is what this directory is for, and
until 2026-08-27 it lived in a session scratchpad, which meant eight rounds of
behavioural proof across five runtimes were narrative rather than re-derivable.

## What is here

| | |
|---|---|
| `build_fixtures.py` | Builds the three fixtures. Run it and you get the projects the rounds were measured on. |
| `TASK.md` | The envelope. Byte-identical across all three fixtures. |
| `expected.json` | What each fixture's report should say, and why. |
| `check_results.py` | Grades recorded reports against `expected.json`. |
| `results/<date>/` | Recorded reports, one per runtime per fixture, plus a `MANIFEST.json` saying how each was invoked. |
| `run-all.sh` | Builds the fixtures, then grades the recorded results. |

## The three fixtures

Each is an ordinary small project — `src/cli.py`, `README.md`, and house rules
in both `AGENTS.md` and `CLAUDE.md` — with sentinels on disk for whatever it is
supposed to have installed, a manifest generated by the project's own
`.aaw/detect.py` against a **fake HOME**, and the routing block merged in by
`tests/packaging/project_ops.py install`. The block is the installer's output,
never placed by hand.

**`all-installed`** — the positive control. All three components installed; the
routes should fire. It is also the only fixture where `gstack` (true) and
`gstack-to-plans` (false) diverge, which is what proves a runtime reads
per-component rather than per-vendor.

**`only-superpowers`** — the decoy. superpowers only, plus a
`.advanced-plans/specs/borrowed.md` sitting in plain sight. The block says a
directory is data, not an installation. A runtime that infers from the folder
routes to Advanced Planning and fails.

**`broken-manifest`** — the discriminator. Every sentinel is genuinely on disk
and global gstack is visible in the fake HOME, but `.aaw/installed.json` is
truncated and unparseable. The block says that means treat everything as not
installed. A runtime that probes the filesystem gets all three requests wrong.

**Never run `broken-manifest` alone.** `NONE`×3 is also exactly what a runtime
that never read the block produces. The positive control is what tells those two
apart, which is why every round runs all three.

## Running it

```bash
python tests/adherence/build_fixtures.py --out /some/scratch/dir
python tests/adherence/check_results.py
```

or both at once:

```bash
bash tests/adherence/run-all.sh
```

On Windows, `bash` at a PowerShell prompt is **WSL**, not Git Bash. Call Git Bash
by path: `& "$env:LOCALAPPDATA\Programs\Git\bin\bash.exe" tests/adherence/run-all.sh`.

`build_fixtures.py` refuses to build inside the repository. `check_results.py`
exits 0 when every recorded result matches or is a known divergence, 1 on a
mismatch or a fabrication, 2 if it could not run at all.

## Running a new round

The measurement itself is not automated and cannot be: it needs live model
calls, and two of the five runtimes need a permission flag only an operator can
grant. The procedure is:

1. Build the fixtures into a scratch directory.
2. For each runtime and each of the three fixtures, run the agent in that
   fixture's directory with `TASK.md` as the prompt, with `HOME` pointed at the
   fixture's `_home-*` directory so global tooling cannot decide the answer.
3. Save each `ACC-RESULT.md` as `results/<date>/<runtime>--<fixture>.md`.
4. Write a `MANIFEST.json` recording the invocation, model and `mode` for each
   runtime. **`mode` matters**: a read-only run cannot write a spec file, so
   `check_results.py` skips the SP-1 location assertion for it and says so
   rather than failing the runtime for a permission it was not given.
5. Run `check_results.py`.

The invocations that worked, recorded in the manifests:

| Runtime | One-shot invocation | Mode |
|---|---|---|
| codex | `codex exec -s workspace-write --skip-git-repo-check --cd .` | write |
| claude | `claude -p` | write |
| opencode | herdr worker, one worktree per fixture | write |
| cursor | `cursor-agent -p --trust --mode ask --model auto` | read-only |
| agy | `agy --mode plan --dangerously-skip-permissions --model … -p=` | read-only |

`--trust` clears cursor's workspace-trust gate but grants no tools; writes need
`-f`/`--yolo`. agy has no per-invocation read-only grant at all. Both are
recorded as B13 in `herdr-ops/FINDINGS.md`.

**Pin the model.** agy's default is `gemini-3.7-flash-high` and it follows the
head of the catalogue rather than a stored setting, so an unpinned re-run does
not reproduce a pinned one — and may not reproduce itself twice.

## What the checker checks

**Expectation match** — is `routed_to` in the allowed set, does the spec go where
the block says, is the terminal step the one the block routes to.

**Fabrication** — every command or skill named in `routed_to` or `terminal_step`
must appear verbatim in the block. A runtime that invents a plausible-sounding
command has failed even if the command would have been a good idea. This is the
check that catches the failure the manifest gate exists to prevent.

Grading is on the **first** name a field mentions, not every name in it. A
runtime that answers *"write the plan in conversation — not `/new-phase`, not
`writing-plans`, neither is installed here"* has given the right answer and
named three commands doing it; grading the whole set would accuse it of taking a
route it explicitly declined.

## Known divergences

`expected.json` describes the **current** block. A recorded result can fail it
because the block changed, which is not the same as the runtime being wrong.
Those cells are listed under `known_divergences`, reported as `DIVERGED`, and do
not fail the run — so a genuine regression still turns the check red.

There are four right now, all the same cell: `only-superpowers` request 2, where
opencode, claude, cursor and agy named `writing-plans` as the terminal step and
codex checked the disk, found the skill absent, and declined. codex was right and
the block was silent; `c83c90e` closed it. Re-running `only-superpowers` against
the current block is what clears those four.

Deleting an entry from `known_divergences` without re-running the round is how a
checker stops being a check.
